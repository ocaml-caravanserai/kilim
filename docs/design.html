Summary

The ocaml-caravanserai organization has three libraries: caravan (HTTP server and web framework), weft (structured concurrency) and windtrap (tests). kilim is the library for the browser side. kilim does not depend on weft.

kilim has three main ideas:

  • The Elm architecture (TEA). A model, typed messages, a pure update and a view function.
  • Encapsulated components. A component keeps its own model, messages, tasks and subscriptions. The parent sees only typed props and typed outputs. The compiler enforces this through the .mli file.
  • No OCaml effects. Event handling and rendering are synchronous. An async task is a value of the type 'a Async.t, written with let*. The runtime gives each task a cancel token. The tokens make a tree: an unmount cancels the token of the component, and thus all of its tasks, timers and requests.

Because kilim performs no effects, the two compilers use their default modes, with no CPS transform. The core is pure OCaml with no browser dependency, thus the tests run native with a fake DOM and a virtual clock.

Decisions

Async and effects
No weft. No OCaml effects.

Commands are values. Async tasks use 'a Async.t with cancel tokens and a trampoline.

DOM bindings (draft 7)
Brr + kilim.web, no JS file

Brr for the Web APIs. Jv bindings in kilim.web for the gaps. The diff calls Jv with literal names and literal arrays. The compilers change these calls into direct JS calls.

Targets
js_of_ocaml + wasm_of_ocaml

Default modes of the two compilers. No CPS, because kilim performs no effects.

SSR and hydration
After version 1

The view type can render to a string from the start.

Name
kilim

The opam package and the repository name.

License
MPL-2.0

The same license as caravan.

Tasks and interop
Tasks only send, Fut only

A task cannot read the model. The only interop for Async.t is of_fut for Brr Fut.t.

Components
OCaml 5.5 module-dependent functions

Component.v (module Counter). Outputs through Ctx.emit. Shallow props equality by default.

Runtime (draft 26)
One turn for each callback

Each callback runs one turn: settle the two queues, then render. A discrete event renders at once. Other renders wait for a frame or 100 ms. A limit of 50 ms of busy time.

Model change (draft 20)
Physical equality

An instance is dirty when update gives a model that is not physically the same as the old model (Object.is under js_of_ocaml). No structural equality on models.

Lifecycle (draft 7)
An alive flag for each instance

A message goes to an instance object. The runtime drops each message to an unmounted instance, also with no token.

Scope of version 1
Smaller again

No Cmd.msg, no Cmd.run, no props_changed, no View.lazy_. Handles, Store, Component.any and slots come after version 1.

Why no weft

After draft 4, weft ran only the async tasks. kilim's main promise, components that stop their own tasks, does not need fibers. weft cost these items:

  • Fibers in the browser need OCaml effects. Effects need the CPS transform on the two targets, and CPS makes all code slower and larger.
  • wasm_of_ocaml --effects=native (Wasm stack switching) removes the CPS cost. But at this time it runs only in Chrome 148 or later with an experimental flag.
  • The default jspi mode refuses effect handlers in JS callbacks.
  • weft needed a new driver entry point and time slices. The core of weft also links multicore code that the browser does not use.

Without weft, kilim loses direct-style async code, CML events and the weft simulator. A small task type with let*, cancel tokens and a virtual clock replaces them (section 12).

Goals and non-goals

Goals

  • A typed TEA core with a pure update.
  • Components that encapsulate state, messages, tasks and subscriptions.
  • Synchronous event handling and rendering.
  • Async tasks with cancellation by component, and no OCaml effects.
  • Deterministic tests without a browser.
  • Two targets from one code base, in the default modes of the compilers.
  • No memory growth: after a mount and an unmount, no token, timer or listener stays alive.
  • Performance budgets that the CI checks (section 16).
  • A view type that can render to a string, for SSR after version 1.

  • Handles and public actions (api). Props do the same task.

  • View.lazy_. A component with equal_props does the same task.
  • Test queries by ARIA role. Queries by label, text and test id do most of the same task.
  • Slots (children of a container component).
  • Direct-style async code and an integration with weft.
  • SSR and hydration, a CSS system, a JSX-like PPX, native mobile targets.

val Kilim_browser.run : mount:string -> App.t -> unit
(* Starts at once if the mount element exists. If not, and the document is "loading",
   it waits for the first readystatechange: then a missing element goes to the error handler.
   If the document is not "loading", it raises Invalid_argument. The loader starts the build

An error in init, update, view, a task, a message function or a DOM operation of the app goes to the root catch (section 09). The root catch unmounts the App: all of its tasks stop. Then the root shows fallback exn. The messages of the root fallback do nothing, because the App is not alive. A component in the root fallback mounts dead: its init runs for its view, its commands do not run, and its messages are dropped. With no ?fallback, the root shows an empty text. An error in the root fallback goes to the console, and the root then shows an empty text. This is also true when the write of the fallback raises, for example for a duplicate key in View.keyed. If the write of the empty text also raises (a DOM fault), the root removes its DOM. This is a best effort: a fault of the host can leave a part of the DOM.

Cmd: commands

update stays pure. It gives a command as a value. The type 'msg Cmd.t has one parameter, as in Elm.

Cmd.none
Cmd.batch [c1; c2]
Ctx.emit ctx out              (* components only: an output for the parent, in the same turn *)
Cmd.task t                    (* t : msg Async.t; its result is a message *)
Cmd.latest ~key:"search" t    (* as task, but cancels the old task of the key in this instance *)
Cmd.map ?scope:"left" f cmd   (* scope: a level of the key path of Cmd.latest in cmd *)
  • Ctx.emit puts the output at the back of the queue, as a message of the parent.
  • A task command becomes a task request. The runtime starts the task in the settle step of the turn, after the messages, with a new cancel token (section 12).
  • The keys of Cmd.latest are local to the instance. When update gives a task with a key, the runtime makes the token of the new task at once, under the instance token, and it cancels the token of the old task with that key, also if the old task has not started. The new task starts later, in the settle step, with that token. When the result message or the error of a task leaves the queue (processed or dropped), the runtime removes the key from the table if the key still points to that token. The key does not leave when the task ends, because its result can still wait in the queue, and a newer task with the same key must cancel it. Thus an instance that uses many keys (for example "save/" ^ id) keeps no entry for an ended task. A leak test sends 1,000 distinct keys to a live instance, and the table must be empty at the end. Thus a result of the old task that is already in a queue is dropped, also after a yield. If one component has two sub-parts under two Cmd.map, give each Cmd.map a different ?scope. Then the same key in the two parts does not collide. A key under ?scope is a path (the scopes, outer first, then the key), not a joined string. Thus a scope never collides with a key that contains "/": Cmd.map ~scope:"a" (Cmd.latest ~key:"b" t) and Cmd.latest ~key:"a/b" t are two keys.
  • Each queued message keeps its instance and the token of the task that sent it. When the message leaves the queue, the runtime drops it if the instance is unmounted or the token is cancelled. Thus a stale result of Cmd.latest and a late message after an unmount do nothing.
  • Version 1 has no Cmd.msg. A message from update to itself can loop forever and needs more ordering rules. Call your update function again in your own code.

Sub: declarative subscriptions

subs gives a set of subscriptions with keys. At the end of a render, the runtime compares the new set with the last set:

  • A new key starts the subscription with a new cancel token.
  • A removed key cancels its token.
  • A key that stays keeps its subscription. For Sub.every and Sub.window, the runtime gives it the new message function through a mutable cell, thus its messages use the newest mapping. A payload takes the message function when it leaves the queue.
  • Sub.every and Sub.window need no key. The runtime makes their key from their parameters: the interval, or the event name. If two of them have the same parameters, the runtime adds their position among them to the key. Each of them is a private kind of subscription with a type witness. The key has the witness, thus the same key always has the same kind, and Sub.every and Sub.run keys never collide.
  • Sub.every span msg has a fixed delay, not a fixed rate: the next timer starts after the delivery of the last one. It refuses a zero span with Invalid_argument.
  • Sub.window is in Kilim_browser.Sub, which includes Kilim.Sub. It uses a private kind of subscription with no key. Sub.window name f listens to name on window with a passive listener, because the message function runs after the dispatch and cannot prevent the default. Each event is a payload, and the newest f of the key makes the message when the payload leaves the queue. The event runs a microtask turn, thus the render waits for the next frame. The task never ends by itself: the cancel of its key (a removed key, an unmount, a stop) removes the listener. An app module that uses Sub.window links only in the browser builds, thus kilim.testing cannot run it: give the window subscriptions to the app as a parameter. A later phase can add a window kind in the core whose payload each platform makes. kilim.browser and kilim.testing share one event dispatch (Private.Event.dispatch).
  • Sub.run needs a key. Its function is opaque, thus each parameter of the function must be in the key, for example the room. Its send has no mapping. If its task ends, the key stays, and the task does not start again. A send after the cancel of the key, or after the unmount of the instance, has no effect, also when the task ended.
  • Version 1 has no Sub.map: a kept key of Sub.run cannot take a new mapping with a safe type.
  • A duplicate key of Sub.run raises Invalid_argument (error scopes: section 09).
  • The runtime starts new keys at the render. If a turn ends with a render that is pending, the runtime calls subs for the changed instances at the end of the turn. It stops the removed keys and removes them from the recorded set, and it gives the new message functions to the keys that stay (section 11). Thus a removed subscription sends no more messages, a kept one uses the newest mapping, and a new one sees the newest props.
let subs _props m =

Component.Defaults gives subs and equal_props.

Props equality. The default equal_props is Component.shallow_equal. It compares two records one field at a time, as React.memo does. Its contract: if it gives true, the two props give the same view. A false result for equal values costs only one more render. The field compare depends on the build:

  • Native code and wasm_of_ocaml: the compare reads the tag of the value first. It uses String.equal for a string and a compare of the bits for a float, also in a record with only float fields. Thus 0. and -0. are not equal. For all other values, it uses physical equality (==).
  • js_of_ocaml: a float, an int32 and an int are JS numbers with no tag, and a string is a JS string. Thus kilim.browser installs Object.is as the field compare in this build. Object.is compares strings and numbers by value, keeps 0. and -0. apart, and compares blocks by identity.

The field compare hook. A global hook in the runtime keeps the field compare, because shallow_equal is a plain function with no runtime env. The hook has the type {same: 'a. 'a -> 'a -> bool}, thus its interface has no Obj.t. The default is a == b || by_tag a b, with by_tag the compare by tag of the list above. In a record or an array of floats, the default compares the bits of each float with no allocation. kilim.browser replaces all of the field compare with Object.is one time, at its top level, in the js_of_ocaml build. The other builds keep the default. Two facts of js_of_ocaml make by_tag incorrect there: 0. == -0. is true, and the tag of a JS array that starts with an unsigned integer is that integer. Thus by_tag would find the JS arrays [253, 1] and [253, 2] equal, as two NaN floats (tested). Under wasm_of_ocaml, (==) gives true for two equal JS strings and false for the JS numbers 0 and -0 (tested).

The rule "0. and -0. are not equal" holds in native code, under wasm_of_ocaml, and under js_of_ocaml with kilim.browser. A js_of_ocaml program without kilim.browser, for example a test with kilim.testing, keeps the default compare: == and the compare by tag. There == is ===, thus 0. and -0. can compare equal. Also a JS array that starts with an unsigned integer can take the compare by tag: for example the JS arrays [253, 1] and [253, 2] compare equal, as two NaN floats. The model compare of the test host is (==) too (item "Model change" below).

With == only, a string that view builds is equal under js_of_ocaml and not equal in native code. Also 0. and -0. are equal under js_of_ocaml, and the view then keeps a stale value. The compare scans the fields only of a block with a tag below Lazy_tag (a record, a tuple, a variant). A closure, an object, a lazy value that is not forced or a block with no scan has no field scan: the field compare alone decides. In native code, a forced lazy value can become its value, and then it compares as its value. Under js_of_ocaml, a JS function has the tag of a closure, and its "fields" are undefined. Thus a scan would find two different functions equal. A sketch of the rule above gave the correct result for 13 cases in native code and under js_of_ocaml, also for 0. and -0. and for two different closures. Some results can still differ by build, but only in the safe direction: two equal int32 values, or two NaN values with different bits. Props must be immutable: a mutable field that changes in place compares as equal. The compare uses Obj inside the runtime. If the props are equal, the instance does not render. The ~on function of the parent is never compared: the runtime replaces it on each render of the parent.

Outputs through a context. The runtime gives update a context of the type (msg, out) Ctx.t. Ctx.emit ctx out puts the output in the queue as a message of the parent, in the same turn. init does not get a context, because an output during a mount is usually a design error.

Reset by key. Version 1 has no props_changed. To reset a child, the parent changes the key of the child. The runtime then unmounts the old instance and mounts a new one, and init runs again.

Rules

  • Encapsulation. The .mli file keeps model and msg abstract. The compiler refuses each access from the parent.
  • Identity. The identity of an instance is its parent instance, its place and C.id. The place is the absolute position among its siblings, the same position that the DOM diff uses. Inside View.keyed, the key replaces the position, thus a move does not remount. Outside View.keyed, the ?key of Component.v only resets: a new key at the same position remounts. If the key or the id at a place changes, the runtime unmounts the old instance and mounts the new one.
  • Duplicate keys. A duplicate key in View.keyed raises Invalid_argument before the diff writes the DOM. The old list has no duplicate, because the runtime checked it. The diff compares the common start and the common end of the two lists. If the new middle is empty, the new list is the old list with some keys removed, thus it has no duplicate, and the diff does no check. If not (an insert or a move), the diff puts the keys of the new middle in a hash table of kilim before it writes, and it finds each key of the common start and end in this table. If the searches of the patch read too many slots of the table, the diff uses a Map in place of the table (section 11). The prefix and suffix passes of ivi alone do not find a duplicate. For example, old [1; 2] and new [1; 1; 2] have an empty old middle, thus ivi does no middle pass, but the new middle [1] is not empty.
  • Two edge cases of identity. A component module made inside view (a local module or a functor application) gets a new id on each render, thus it remounts each time. Two modules that share one id (for example by include) do not remount when they change places. Do not do these things.
  • Mount. The runtime calls init. Its commands become task requests.
  • Cancel tokens. When update or init of an instance gives its first task command, or the instance starts its first subscription, the runtime makes its token. If an ancestor has no token yet, the runtime first makes the tokens of the ancestors, from the top. Thus the token of a child is always under the token of its parent. A token made under a cancelled token is cancelled at once. An unmounted instance gets only a cancelled token.
  • Alive flag. Each instance has an alive flag. A queued message points to its instance object, not to a path in the tree. When the message leaves the queue, the runtime drops it if the instance is not alive. This rule covers instances with no token, tasks that ended before the unmount, and DOM events. At the unmount, the runtime clears the model, the last view, the DOM references and the children of the instance. Only the flag and the id stay. Thus a JS callback that never runs (for example a promise that never settles) keeps only a small object alive, not the subtree.
  • Unmount. The runtime clears the alive flag of the instance and of its children, removes them, and cancels their tokens. Thus all tasks, timers, requests and subscriptions of the instance and of its children stop. The mount, the patch and the unmount of nested instances are recursive. The supported depth is 500 nested components, each with an element (tested in the three builds). Under js_of_ocaml on node 24 with the default stack, the first patch of a chain of 650 levels overflows the stack, and 600 levels work.
  • Model change. An instance is dirty when the model that update gives is not physically the same as the old model, as Elm does for lazy. The compare is the field same of the runtime env: the identity of the platform. In native code and under wasm_of_ocaml, it is (==): under wasm_of_ocaml a float is a box, thus (==) keeps 0. and -0. apart, and its only error is one more render. Under js_of_ocaml, == becomes ===, and a float model is a JS number: then 0. and -0. would be the same value, and the render of a real change would be missed (tested). Thus in the js_of_ocaml build, kilim.browser gives Object.is, which is the identity of JS values. It picks the compare one time, from Sys.backend_type. Object.is keeps 0. and -0. apart, and it costs one JS call (about 4 ns) for each update. Under wasm_of_ocaml it costs 39 ns and compares the boxes anyway, thus that build keeps (==). The test host gives (==). Phase 2 uses the same identity for the props compare: in the js_of_ocaml build, kilim.browser also gives Object.is as the field compare of Component.shallow_equal (section 09). The runtime never uses structural equality (=) on a model. A test with OCaml 5.5 and js_of_ocaml 6.4.1 showed why: = raises on a closure in the model, gives true for 0. and -0. (a missed render), gives false for nan, walks the whole model on each message, and loops on a cyclic value. Physical equality costs one compare, never raises, and its error is in the safe direction in each build: a new model with the same content costs one more render. update gives back the same model when nothing changed. The model must be immutable: if update changes a mutable field in place and gives back the same model, the runtime does not render.
  • Props. If equal_props gives false, the runtime renders the instance again.
  • Outputs. The ~on function of the parent changes the output into a message of the parent, in the same turn.

After an error in an instance, the runtime goes to the nearest View.boundary above it. It unmounts the whole subtree of the boundary, and thus cancels all of its tokens. Then it puts the fallback view in the DOM node of the boundary. With no boundary, the root does the same with the ?fallback of App.make, and the runtime writes the error to the console. Section 08 gives the rules of the root catch. The runtime gives the exception to console.error as a raw value, because Printexc links Printf.

State of a boundary. A boundary is a node in the retained tree of its parent instance. After an error, it keeps the exception and the fallback subtree. It keeps the fallback until its place remounts: a key change, or a change of the node kind at its place. A new render of the parent calls fallback exn again and diffs the result with the fallback subtree. The fallback uses the context environment and the outer boundary that the boundary recorded at its mount. Thus a fallback that a catch builds outside the diff of the parent gets the same providers as the child had. It does not try the failed child again, as in React. To try again, change the ?key of the boundary. An error in the fallback subtree goes to the next boundary above, not to the boundary that shows the fallback, as in React. Thus a fallback that raises cannot cause a loop of remounts.

val View.boundary : ?key:string -> fallback:(exn -> 'msg View.t) -> 'msg View.t -> 'msg View.t

View.boundary and Context.provide take one child, not a list. Thus each view node maps to exactly one DOM node, and the diff of Phase 1 needs no fragments. Put a list in an element, for example El.div.

Example: a search box with debounce and cancel

Each key press starts a new Cmd.latest task with the key "fetch". The new task cancels the token of the old task. If the old task waits in Async.sleep, its timer stops. If its request is in flight, the browser aborts it. A result that is already in the queue keeps the cancelled token of the old task, thus the runtime drops it.

Shared state

Context.t is a typed key. A provider in the view gives a value to all components below it. During view, Context.read records the instance that reads the value. The runtime compares a new provided value with the old value by Component.shallow_equal. If the value changed, the runtime marks only the readers as dirty. A reader renders also when its parent skips it because of equal_props. The other components below the provider do not render.

The data of the runtime for Context:

  • A provider is a view node with one child and no DOM element of its own: its DOM node is the DOM node of its child. It keeps its last value and a doubly linked list of its readers. It moves with its node in a keyed move.
  • A provider and a boundary are node kinds in identity. If a provider or a boundary appears or disappears at a place, or the context of a provider changes, the subtree at that place remounts, as in React. Thus a reader never keeps a context environment that points to a removed provider.
  • Each instance keeps its context environment from its mount: a map from the context id to the nearest provider above it. Thus the runtime can render a reader alone.
  • Each render of a reader removes its old registrations and adds new ones, because a read can be conditional.
  • The diff keeps the providers on its path. A Context.read node gets the nearest provider on this path, also a provider in the same view. If no provider is on the path, it gets the environment of its instance. The read registers with that provider.
  • When a provider unmounts, its readers unmount too, because they are below it. An unmount removes each registration of the instance from the reader list of its provider, in O(1). The leak tests also count these registrations.

This machinery is in the scope of Phase 2, with tests for a provider in a keyed move, a provider that unmounts, and a conditional read. Version 1 has no Store: a context with a value in the model of the app does the same task.

Runtime semantics

The whole runtime is synchronous and single-threaded. It has no scheduler and performs no OCaml effects.

A turn

The runtime has two queues: the message queue, and the run queue of Async. A turn is the only way to process them. Each DOM listener and each host callback (timer, fetch, socket, frame) runs one turn. A turn never nests: an event that a DOM operation causes (for example focusout on a removed element) only goes into the message queue. A turn has these steps, in this order:

  1. For a DOM event, the listener applies the static options (~prevent_default, ~stop) at once.
  2. Settle. The runtime does the three settle actions again and again, until the two queues and the list of task requests are empty.
  3. Render. For a discrete event (click, input, change, submit, keydown), or for a frame turn, the runtime renders at once. A frame turn renders if a render is pending or if its own messages changed a model. A frame of a task is a frame turn. In all other cases, the runtime marks a render as pending (see the rules that follow).
  4. The render can give new work: a focusout, the init tasks of new instances, the first message of Sub.run. Then the runtime settles again (step 2). If the settle changed a model, the runtime renders again at once. One turn has at most 3 renders. After the third, the rest waits for the next pending render.

The three settle actions are:

  • Drain the run queue. A continuation can put a message in the message queue.
  • Take one message. Drop it if its instance is not alive or its token is cancelled. If not, call update, and mark the instance as dirty if the new model is not physically the same as the old model. An output of Ctx.emit goes to the back of the message queue.
  • When the message queue is empty, apply the task requests in the order of their creation. The init tasks of new instances also start here, after the render, and at no other point. A task with a synchronous result gives its message in the same settle step.

Subscriptions in a turn. In a discrete turn and in a frame turn, the render follows the settle at once, thus the render alone compares the subscriptions. If a turn ends with a render that is pending, the runtime calls subs at the end of the turn for each instance whose model changed since its last call of subs, with its stored props. It cancels the keys that are gone and removes them from the recorded set, and it gives the new message functions to the keys that stay. Thus a key that comes back before the render starts again at the render. A removed subscription sends no more messages, and a kept one uses the newest mapping, before the render. New keys start only at the render, with the newest props. If the render then changes the props, the worst result is one restart of a subscription. The end actions of this call can push work (an ok, a send of a key that stays): the runtime settles it in the same turn. After a stop at the limit, the continuation settles it. A message that a removed key pushed before its cancel is dropped when it leaves the queue. In the turn of the change, the messages that leave the queue before the end of the turn are still processed.

Thus one click renders one time, also when its update starts a task with a synchronous result. A render that mounts children with synchronous init tasks renders again, at most 3 times in one turn. A sketch of this turn passed these tests in the two builds:

  • A result of Async.make in a click, in a timer callback and in a raw callback, and a Sub.run send from a raw callback: each message is processed in the same turn, with one render.
  • Five levels of mounts with synchronous init tasks: 3 renders in the click turn, 3 in the next frame turn, then none.
  • A message loop through microtasks stops after 50 ms and continues in a new task. After 10 stops at the limit in 1 s, a warning goes to the console.
  • 10 promise results after 0.5 s, 1.5 s or 2 s of idle time (the tick runs before the idle time), and 500 raw callbacks 1 ms or 2 ms apart: each one is processed in its own turn, with no yield and no warning.
  • A task that loops through synchronous make steps, or through microtasks with no message: the drain stops at the limit, and the turn yields one time.
  • A promise loop with 5 ms of JS work outside kilim in each step: the wall-time cap stops it after 1 s, with one yield.
  • One event gives messages to two widgets. The update of Y changes its model, then the update of X raises: the error goes to the boundary of X, and Y renders in the same turn.
  • A search box gets "ab", and then the result of "a" comes in the same turn: the result of "a" is dropped. Two key presses in one turn, before the first request starts: the first request never starts. A yield leaves the last continuation of "a" in the run queue, then "ab" comes: the result of "a" is dropped. 1,000 distinct keys on a live instance leave an empty table.
  • A model of the instance tree: a card that renders alone and raises goes to its own boundary, and the other dirty instance still renders. Rows 4 and 5 mount with Sub.run, then row 6 raises: 0 live instances and tokens stay. A nested boundary in the same view: the outer catch also unmounts the inner subtree. All rows of a list fail, each in its own boundary: the time is linear. A fallback that a catch builds gets the provider of its place. An error in a fallback goes to the outer boundary. 1,000 replacements of 100 rows add 0 links. 1,000 pages of 20 cards, each with its own boundary, leave 0 nested entries. An unmount leaves 0 reader registrations. A key that stops and starts again before the render is live after the render.
  • An input event in a turn that yields: no restore in that turn, and one restore after the next render.
  • 10,000 init tasks in one turn: one yield and no warning.
  • An exception in the render: the next turn runs normally. If work stays in a queue, the runtime asks for a new turn.
  • A keyed diff from [1; 2; 3] to [3; 2; 4] where row 2 raises in its boundary: the DOM is [3; 2 (fallback); 4], row 1 is cancelled, and the init task of row 4 is requested.
  • A change of the room in a non-discrete turn: the old subscription stops at the end of the turn, before the render, and its next message is dropped.
  • Outside a turn. A binding can call ok, and Sub.run can call send, from a callback that kilim does not wrap (for example a raw Ev.listen or an IndexedDB request). Then the push to a queue asks the host for one turn in a microtask. A flag prevents a second request before that turn runs. After the catch of a turn, the work that stays asks for a microtask turn. The runtime calls the host before it sets its flag (a turn is requested, a continuation is posted, a tick is pending, a render is scheduled). Thus a fault of the host leaves no flag with no callback. When no turn runs, a pending render always has a scheduled callback.
  • Time limit. The limit counts the busy time of kilim turns, not wall time. Each turn adds its duration to a busy sum. The settle step stops when the busy sum is more than 50 ms (a strict compare). It examines the limit before each settle action and at each clock read of the drain. Thus a turn with no work never stops. The check before each settle action is the only limit on a chain of slow updates. It costs one clock read for each message: about 150 ns in wasm_of_ocaml with performance.now. The end of each turn posts one tick (a MessageChannel message, at most one at a time). The tick is not a turn: it only clears its own flag and sets the busy sum to 0, and it posts nothing. A turn starts a new clock (busy sum 0, and the wall-time window starts) if it is a macrotask turn (a DOM event, a timer, a frame, a post_task continuation), or if no tick is pending. No pending tick means that a browser task ran since the last turn. Thus results that come from foreign tasks (IndexedDB, raw listeners, streamed chunks) add only their own small cost, and they never yield with no progress. A microtask chain never lets that message run. Thus a message loop through microtasks adds busy time and stops. A wall-time cap stops a chain whose time is outside kilim (for example a promise loop with long JS work in each step): if 1 s of wall time passes in one chain with no reset, the runtime yields. A result after idle time gets a new clock, because its tick ran before the idle time, thus the cap does not make it yield. The drain of the run queue reads the clock before its first continuation and once every 256 continuations. Thus a task that loops through synchronous steps, or through microtasks with no message, also stops. At the limit, the runtime keeps the rest in its queues, marks a render as pending, and continues in a new task (host.post_task). It posts at most one continuation: a stop while a continuation is posted posts nothing. A frame turn or another macrotask turn can drain the run queue and start a new chain while a continuation is posted, and that chain can also stop. A large mount of 10,000 rows can yield one time, with no error. Each stop at the limit goes into a ring of the last 10 stop times, also a stop while a continuation is posted. When the ring has 10 stops in 1 s, the runtime writes one warning to the console. It writes a warning again only after a stop that finds fewer than 10 stops in the last 1 s. Thus one loop gives one warning, not one for each stop.
  • Exceptions. At mount, each instance records its nearest boundary, as it records its context environment. Each boundary is a record in the retained tree. At its mount, it records its owner instance, the next boundary above it (its outer boundary), and the context environment on the diff path at its place. The diff puts the child of each View.boundary in try ... with (not Fun.protect). Each render of a dirty instance alone (its own model changed, or it reads a Context) is also in try ... with, and so is each call of update and of subs for one instance. After an error in update, the settle step continues with the next message. Thus a model change of another instance in the same turn still renders. Each boundary catch that is not inside the diff marks a render as pending: a catch in update, in a task step or a callback of Async.make (in the drain), or in the early call of subs. Thus the subscriptions of the fallback start at that render. A catch in the subs pass at the end of a render starts the subscriptions of the fallback instances in the same pass. The error goes to the recorded boundary. On an exception from user code or from a DOM operation, the boundary unmounts its subtree, builds the fallback with its recorded environment, writes the fallback into its DOM node, and the render continues. The instances of the fallback record the outer boundary. The diff of the parent continues with the other siblings, and the render skips the dirty instances that the catch unmounted. The root has the same catch, with the ?fallback of App.make. The turn has one more try ... with for errors outside the render. After that catch, the runtime clears its turn flags. If work stays in a queue, it asks for a new turn. If an instance is dirty, it marks a render as pending (a discrete turn renders at once).
  • Link before init. The diff links a new instance into the child list of its owner instance, and into the member list of its boundary, before init runs and before its first DOM write. A boundary also links into the list of nested boundaries of its outer boundary, and into the list of owned boundaries of its owner instance. All these lists are doubly linked, and an unmount unlinks in O(1), as for tokens. The boundary record keeps its own nodes in these lists. The unmount of an instance unlinks its owned boundaries from their outer boundaries. A diff that removes a boundary node, a key change of a boundary, and a catch that removes nested boundaries unlink the boundary from the owned list of its owner and from the nested list of its outer boundary, also when the owner stays alive. Thus the nested list of a long-lived boundary does not grow: in a model, 1,000 pages of 20 cards, each card with its own boundary, left 0 entries. To unmount the subtree of a boundary, the catch walks only its member list and, recursively, its nested boundaries. Thus a nested boundary in the same view, and an instance that a stopped diff mounted, are never outside the unmount. The cost of a catch is linear in the size of its subtree: in a model, 100,000 rows that each fail in their own boundary took 7.5 ms native and 52 ms under js_of_ocaml. The leak tests also count these links, the member lists, the nested lists and the owned lists. One leak test keeps the owner alive and replaces 100 boundary rows 1,000 times: each list must be empty at the end.
  • Start. A loader picks the build and starts it (see "The loader" in this section).

A render

  • Timing. A pending render runs at the next animation frame, or after 100 ms, whichever comes first. Thus a throttled frame (for example in an iframe that is out of view) does not delay unmounts, cancels and new tasks for long.
  • Hidden tab. In a hidden tab, a pending render runs in a new task (host.post_task), not in each callback. Thus a post_task gives at most one render, for all the messages that came before it. When the tab becomes hidden, a visibilitychange listener does a pending render at once. Its turn first clears the scheduled render (the frame and the timer), and it is a frame turn. If that turn stops at the limit, its end schedules the render with host.post_task.
  • The render calls view for the dirty instances, from the top. It mounts and unmounts instances. The diff calls the DOM operations directly, with no patch list.
  • The keyed diff uses the algorithm of ivi and Inferno: it compares the common start and end, uses a hash table only for the middle, and moves nodes along the longest increasing subsequence. The hash mixes the bits of the key. The table has a budget for each patch: the patch can read 8 slots of the table for each key that it adds to the table or finds in it. With usual keys, the patch reads about 2 slots for each key. Only the total is important, not the length of one search: at a load of one half, some searches of 65,536 usual keys read more than 32 slots. Many keys that collide, by chance or by intent, go above the budget, and then the diff uses a Map for that patch. Thus a keyed patch costs O(n) or O(n log n), not O(n2). Keys are int or string (Key.int, Key.string).
  • The diff cancels a removed instance when it removes it. At the end of the render, the runtime starts the subscriptions of new instances. Then it compares the subscriptions of each live instance whose model changed or that got new props, and starts the new keys. The init tasks of new instances start in the next settle step.
  • New subscriptions start only at the render, thus subs gets the newest props, and an instance that the render removes starts no subscription. The cost: for a non-discrete event, a new subscription can start up to one frame later. A removed subscription stops earlier, at the end of the turn.
  • A task request of an instance that the next render removes still starts in step 2, and the unmount then cancels it. Its message does nothing, because the instance is not alive.

The loader

A kilim app starts through a small loader. The loader picks one build, one time, before any build starts. There is no fallback after a start, because the generated launcher of wasm_of_ocaml gives no hook to the loader.

  • Why two builds. wasm_of_ocaml catches a JS exception only through WebAssembly.JSTag. Its runtime has a comment that Safari does not support it yet (I am not sure which versions). Without it, no OCaml handler catches a JS exception, also the handlers inside Brr (for example Json.decode). JSTag depends on the browser, not on the build.
  • Probes. The loader picks the wasm_of_ocaml build only if all of these synchronous probes pass: typeof WebAssembly === "object", WebAssembly.JSTag exists, new WebAssembly.Module on the 8 bytes of an empty module does not throw (it throws under a CSP with no 'wasm-unsafe-eval'), and WebAssembly.validate accepts a module with one GC struct type. If not, it picks the js_of_ocaml build. The probes take about 0.001 ms.
  • Two parts, one script text. The page has the same inline script two times. The head part comes directly after <meta charset> and each CSP <meta>, and before each stylesheet. It runs the probes, stores the selected build in a property of document.documentElement, and adds preloads: the selected build (as="script") and, for the wasm_of_ocaml build in the release profile, the main .wasm (as="fetch", crossorigin). The start part has a data-start attribute and is the last element of the body. It reads the selected build from that property and does not run the probes again. The part that runs second starts the build: if the start part finds no stored result, it sets a flag on document.documentElement and returns, and the head part starts the build after its probes if it finds that flag. In the inline form, the head part always runs first. In the loader.js form, this hand-off is the usual path in Chrome: the defer start part ran before the async head part on each first visit with no slow stylesheet, and on repeat visits when the stylesheets are in the cache (measured in Chrome 157). Firefox 159 did the same on about 7 of 10 repeat visits. Playwright WebKit 27.2 can run an async script after the defer scripts (measured in some runs): then the hand-off occurs. The stored result, the flag and a started mark have the data-base value and the data-js value as a key: two builds in one kilim dist directory have the same base. No part clears the flag: the started mark makes a clear unnecessary. Thus two kilim apps on one page (for example two live examples) each start one time. Under a CSP with no 'wasm-unsafe-eval', each probe compile sends a CSP violation report in Chromium and Firefox, thus one probe gives one report for each page view, not two. Playwright WebKit 27.2 refuses the compile, but it sends no securitypolicyviolation event. An optional data-build="js" attribute skips the Wasm probe for a site that never permits 'wasm-unsafe-eval'. The start part inserts the selected build, which comes from the preload.
  • Stylesheets. The parser holds a parser-inserted script until each stylesheet before it that blocks scripts has loaded or failed, also with its @import. Thus the browser decides which stylesheets the first render waits for, and run needs no rule for stylesheets. A failed stylesheet does not block. A print, alternate, disabled or empty stylesheet link does not delay the start. The reviewer measured this in headless Chrome and Firefox: with a stylesheet or an @import that comes at 1.5 s, the app started at about 1.5 s to 1.7 s with the styled layout. With the other links, it started at 60 ms to 65 ms. The build request started at 8 ms to 11 ms, with one download. A stylesheet that a script inserts does not delay the start in Chrome. Firefox 157 holds the fetch of the .wasm files until it loads, and Playwright WebKit 27.2 holds the scripts and the fetches: there, the start comes after it. The browser decides this, and the loader cannot change it. In Playwright WebKit 27.2, a defer script does not wait for the stylesheets, also for a stylesheet before it. Thus in the loader.js form, the app can start with no CSS layout, and a slow third-party defer script can delay the start (the async head part can run after it). The inline form does not have these differences, thus docs/loader.md tells users with Safari to use it. A change of the loader text can remove the two differences: the start part runs the probes and starts the build itself when the head part did not run, and waits for the stylesheets that block rendering. It changes the CSP hash for each user, thus it waits for the Safari check (open item of Phase 1).
  • Mount. If the mount element exists, Kilim_browser.run starts at once. If not, it waits for readystatechange until document.readyState is not "loading". It does not wait for DOMContentLoaded, because that event also waits for each defer script on the page (for example a tag manager). The reviewer measured this in Chrome: with a slow stylesheet, the build ran while the state was still "loading", and DOMContentLoaded came 700 ms later, after a slow defer script. With the start part as the last element of the body, the mount element always exists.
  • Values. The build-specific values are in data- attributes of the script element, and the script reads them through document.currentScript.dataset: the base, the name of each build relative to the base, the name of the main .wasm (release only), the profile (data-dev) and data-start. The base is a path, and it ends with /: kilim refuses a scheme, // and \ in the base and in the names, and .. in the names. Thus the script text is the same in the two parts, in the dev and release profiles and in each build. Its 'sha256-…' source expression changes only when the loader text changes, and the user adds it to script-src one time. The file src/loader/loader.csp holds the expression: the build reads it, and a test compares it with the SHA-256 of the text (node:crypto). Thus each change of the hash is a line in a diff.
  • URLs. The loader loads only from the origin of the page: a URL of another origin throws, and no build starts. The CSP hash does not cover the data- attributes, thus a copy of the loader that an attacker injects has the same hash. With 'strict-dynamic', a script that such a copy inserts would run. The documentation tells users not to use 'strict-dynamic' with kilim, and to use script-src 'self' and the hash. Thus version 1 has no build on a CDN of another origin. The loader resolves each URL against the base path, never against the URL of the document. Thus a deep link of a router app (for example /users/42) loads the build. The launcher finds its .wasm against its own URL.
  • Trusted Types. One start function inserts the build, and either part can call it (see the hand-off). This function makes a policy with the fixed name kilim-loader and sets the src of the script through it. The policy makes script URLs only for the build URLs that the loader records. A script of the page that runs code can also add to that list (the shared property is on document.documentElement), thus the policy is not a defense against a script that already runs. It prevents the use of the name by another script before the loader. If createPolicy throws (the trusted-types directive does not list the name, or the page has no trustedTypes), the function sets a plain URL. With require-trusted-types-for 'script', the browser then refuses the build. A second createPolicy with the same name throws. Thus the function keeps the policy object in a shared property of the page, and it uses that object again if it exists. Thus the second app of a page makes no second policy. Neither part makes the policy at its top. The documentation tells users to add this name to the trusted-types directive. The href of a preload link is not a Trusted Types sink (tested in Chrome and Firefox), thus the preloads need no policy.
  • Order with other scripts. The build can run before each defer script of the page, in the two forms, because the start part runs before them and the inserted build is async. Thus a JS library that the app uses must be linked into the build, or loaded with a blocking script. In the inline form, the blocking script can be anywhere before the start part. In the loader.js form, it can be anywhere in the document. It must not come before the head part, because it then delays the build download (measured: about 105 ms with a 150 KB library). A library that ships only as an ES module cannot be a blocking script: the app loads it with import() in a task, through a JS expression and Async.of_fut. The documentation tells these rules.
  • A CSP with no hash. For this case, the rule also writes loader.js, with the same two parts: <script src="loader.js" async> before the stylesheets for the probes and the preloads, and directly after it <script src="loader.js" defer data-start> for the start, before the stylesheets and before each other defer script. A defer script runs after the earlier defer scripts, thus at the end of the body it would wait for a slow tag manager (measured: about 1 s). A defer script still waits for each stylesheet that blocks scripts in the document, thus the first render has the CSS. The reviewers measured this position with a 600 ms stylesheet and a 1 s third-party defer script: start at 610 ms to 613 ms in Chrome and at 654 ms to 660 ms in Firefox (6 runs, stable), with the styled layout. The third-party script never delayed the start. The browser requests loader.js one time. This form costs one more round trip before the build download starts. The reviewer measured it with a 400 KB build, a 300 ms stylesheet and a 100 ms server delay: start at 657 ms, against 555 ms for the inline form and 858 ms for a single defer loader. The documentation tells this cost.
  • Release files. A dune rule cannot declare a target whose name comes from its content without the experimental directory targets. Thus the dev profile uses the dune rule, with fixed names and no cache. For a release, a small executable, kilim dist, runs after dune. It copies the js_of_ocaml build, the launcher (next to its .assets directory) and loader.js to names with a content hash. During a deploy that is not atomic, an old server then gives a 404 for a new name, and the browser stores no stale file as immutable. kilim dist fills a template of the HTML page that the user gives (with no change to the script text). The content name has the first 16 hexadecimal characters of the BLAKE2b-128 hash of the bytes before the last extension, for example main.bc.0123456789abcdef.js. The .assets directory of the launcher keeps its name, and it must have exactly one .wasm file (a release build). A file with the same name and other bytes is an error, and kilim dist never removes a file. A JSON manifest for a server such as caravan comes when caravan reads it. The documentation tells users to serve each file with a content name as immutable, the HTML page with no cache, and to keep the files of the last deploy for one more deploy. A repeat visit then starts with no request for the build (measured: 113 ms against 214 ms with a 100 ms server delay).
  • Dev checks. In the dev profile, the loader writes a console warning if a stylesheet comes before the head part, a CSP <meta> comes after it, or the start part is not in its place (a child of the body with only start parts after it in the inline form, thus two apps pass, or directly after the async tag in the loader.js form). The part that runs second calls the checks: then the two parts exist. If it is a start part, the checks wait for DOMContentLoaded (each start part runs before it). If it is the head part (the hand-off of the loader.js form), the defer start part already ran, thus the document is parsed, and the checks run at once. The readyState is not a sure signal: it is "interactive" before the defer start part runs, and a slow stylesheet holds that part.
  • The executable. A library cannot ship a dune rule. Thus the package installs the executable kilim: kilim page fills the template for the dev profile (fixed names and data-dev), kilim loader writes loader.js, kilim csp writes the source expression, and kilim dist writes the release files. The user copies the dune rule of docs/loader.md. The template has two markers: <!--kilim:head--> and <!--kilim:start-->, or <!--kilim:head:ID--> and <!--kilim:start:ID--> for two apps. Each marker must occur one time. In the loader.js form, the head marker gets the two tags and the start marker goes, thus one template serves the two forms. A dev server sends cache-control: no-cache: with no-store, Chrome can request loader.js two times.

The loader, the executable kilim and the dune rule of the user are deliverables of Phase 1, and all examples use them. The loader tests (test/loader) run in Chromium, Firefox and WebKit, in the dev and the release profiles. The test server delays the async tag through a second URL (loader.js?head) to force the hand-off. A list of hand mutants of the loader text runs in CI in Chromium when the loader changes: the loader text has no branch for a browser. The examples use the dune rule of docs/loader.md with no change of its tokens, and test/examples runs their dev pages and their kilim dist output in the three browsers. The list of the cases:

  • The js_of_ocaml build loads and starts after delete WebAssembly.JSTag, after delete WebAssembly, and under script-src 'self' plus the hash (no 'wasm-unsafe-eval'), with a CSP header and with a CSP <meta>
  • A CSP with Trusted Types, with a View.unsafe_html node, in the inline form, and in the loader.js form with the hand-off path, on a first visit and on a repeat visit. The test server delays the head part to force this path, and in the dev profile the loader records which part started the build in a data- attribute of document.documentElement. The test fails if the expected path did not run.
  • Two kilim apps on one page, with and without Trusted Types: each app starts one time
  • A deep link, a body that comes 300 ms after the head, and a slow third-party defer script that must not delay the start
  • Under a CSP with no 'wasm-unsafe-eval': one CSP violation report for each page view in Chromium and Firefox, none in WebKit
  • The loader.js form on a repeat visit with all files in the cache: the app starts, with one probe. Playwright WebKit 27.2 does not use the as="fetch" preload of the main .wasm for the fetch of the launcher: it downloads the file two times, also on a repeat visit, and can log that the preload was not used. The loader keeps the preload for the other browsers. The test permits at most 2 requests and 1 preload message for this file in WebKit, and at most one request for each other URL. DOM rules

  • Controlled inputs. For value and checked, the diff compares the view value with the live DOM property, as React does, and writes only a different value. The browser can change these properties with no write of the diff: the user types, a radio button unchecks the other buttons of its group, a select selects an option. The diff writes the properties after all the other operations of the patch, because a later change of a name, a type or a form can uncheck a radio button. A mount and a patch write the properties in the same order: the order of the end tags of the elements in the document. Thus two checked radio buttons in one group give the same result. The cell of the element keeps the view value. After each discrete event, the runtime restores the controlled properties of the event target from the last view, also when the instance is not dirty. Thus a rejected input does not stay, as in React. Each discrete event adds its restore to a list. The next render step runs the list, after its writes, in the same turn or in a later one. A discrete turn runs the render step also when no instance is dirty, and a discrete event inside another turn schedules a render. If a discrete turn yields before it renders, the runtime does not restore in that turn: it restores after the next render. Thus the input of the user does not get lost. A stop clears the list. A restore does nothing for a node that is not in the document, and its error goes to the console. The other restores of the list still run.
  • Checkbox and radio button. The browser sends input and change after the click dispatch, thus after the restore. For these two types, use Ev.check: it uses the click event, as React does. The listener reads checked before the restore and gives it to the message function. If a listener prevents the default of the click, the browser undoes the toggle after the dispatch. A microtask runs before the undo, and a MessageChannel message runs after it (measured in Chrome). Thus after each click on a checkbox or a radio button, the dispatch posts a task that restores the target (and its radio group) from the view: also with no ~prevent_default in the view, because a listener above the mount element can prevent the default too. With no such task, the box would show the undo, and the view the model, until the next patch. A prevented click on a radio button whose handler removes the checked button of the group: Chrome keeps the target checked, and the removed button stays unchecked. Firefox 157 and WebKit 27.2 keep the target checked too, and they check the removed button again. The task then writes the view values of the group, thus the final DOM follows the view whatever the browser does in its undo. kilim.testing does the same, in the order of the browser: the dispatch, the microtasks, the undo, then the restore task.
  • Select and range input. The browser can change a value with no write of the diff. The selected option of a select follows its node: a change of the options can select a different value. The browser keeps the value of a range input between min and max. A removal of size or multiple from a select with no selected option selects the first option. The compare with the live property finds each of these changes, and the diff writes the view value again. A key that changes the selected option of a focused select (ArrowDown) sends input and change at once in the three browsers, not at the blur (D13).
  • Radio group. A click on a radio button also clears the other buttons of its group. Thus the restore of a radio button also restores the other buttons of its group, as React does. The group follows the form owner: a button with no name has no group. Else the group is the radio buttons in the mount root with the same name and the same form owner (also through the form attribute, from outside the form), or with no form owner for a button with no form owner. The names and the form owners compare as JS values. The query uses the one literal selector input[type=radio], thus a name never goes into a selector. It does not read form.elements, because a control with the name elements hides that property. A button of the group outside the app has no cell, thus the restore does not change it.
  • IME. A write of value stops a composition. Thus compositionstart sets a flag in the cell of the target. While the flag is set and the element has the focus, the diff and the restore do not write value: the cell keeps the new view value. The input messages during a composition still go to update, as in React: only the writes wait. A keydown or a keyup with isComposing runs no handler, thus the Enter that commits a candidate does not submit. Chrome sends each update of a composition as compositionupdate, beforeinput and input (with isComposing), then compositionend after the commit. Firefox sends the last input after compositionend in the same task, with isComposing false, and at compositionend the live value is already the commit (measured in Playwright Firefox 157). A write at compositionend erases the commit. Thus compositionend clears the flag and runs its handlers in a Macro turn, which does not render. Then it posts a task with a discrete turn that only restores the target, as a click on a checkbox does. In the order of Firefox, the last input renders first. In the order of Chrome, the task renders. The flag does not stay set until the task. In Chrome, compositionend and a new compositionstart can come in one task (two compositions in a chain). Then the task finds the flag set again, and the restore waits until the last composition ends. The final value is correct.

    Chrome sends no compositionend when it moves or removes the composing input, but it sends focusout. Thus a focusout or a focusin on a target with the flag also clears it and restores the target (a composition always starts after a focus). An input with isComposing false does not clear the flag. Firefox and WebKit send no focusout on a move or a removal of the focused input (measured in Playwright Firefox 157 and WebKit 27.2), and Playwright cannot show if they send compositionend. But in the three browsers, the element loses the focus, and a composition cannot go on in an element with no focus. Thus a write site of the diff that finds the flag on an element with no focus clears the flag and writes. This rule does not depend on the browser. The diff reads the focus only when the flag is set: the node is the activeElement of its root node (the document, or the shadow root of an app in a shadow tree).

    Playwright has no composition command for Firefox and WebKit. In Firefox, its text input is a real composition, in the order above, thus D7 and D39 test the order of Firefox (D39 with a render that waits at compositionend). In WebKit, its text input is an input with no composition. Not sure, for the Safari check of Phase 0: the order of a composition in Safari, and a keydown with keyCode 229 after compositionend, which the isComposing rule does not cover. No change of the isComposing rule: on Android, each key of a text input can have keyCode 229.

  • Events that do not bubble. focus and blur use focusin and focusout. mouseenter, mouseleave and scroll use listeners on their elements. The field bubbles of a handler is false for these events and for touch and wheel: false means a listener on the element. The mount element has one listener for each other name: click, input, change, submit, keydown, keyup, focusin, focusout, compositionstart and compositionend. A removed element keeps its cell and its listener, and the browser can send it an event later (for example scroll), thus a listener on an element does nothing for an element that is not connected.
  • Touch and wheel. Ev.wheel, Ev.touchstart and Ev.touchmove (no payload in version 1) use listeners on their elements, not delegation at the root. The listener is passive if the handler has no ~prevent_default. Thus a scroll over the app does not wait for the main thread. A passive listener cannot prevent the default (measured). addEventListener with the same function ignores a new passive, thus a patch that changes ~prevent_default removes the listener and adds it again.
  • One dispatch. Private.Event.dispatch in the core holds the rules of the events: the payload, the prevent and the stop, discrete or not, the restore, the IME rules and the restore task after a click on a checkbox or a radio button. kilim.browser and kilim.testing each give only an env (the parent, the cell, connected, the radio group, the task) and the event. Thus the native tests and the mutation tests reach the rules that the browser uses. The events of a removal depend on the browser: Chrome sends change (for a dirty value), blur and focusout inside removeChild, and Firefox 157 and WebKit 27.2 send no blur, no focusout and no change on a move or a removal of the focused input, and the element loses the focus (D22 counts 1 blur message in Chrome and 0 in the two others). Thus kilim does not promise an Ev.blur message on a removal. The restore of such a change finds the node not connected and writes nothing. A turn never nests: an event inside a turn only reads its payloads and queues them. A kilim app inside the DOM of another kilim app is not supported, because the outer walk would read the cells of the inner app. Apps side by side work: each one has its own DOM operations and its own listener functions. One element has at most one live app: a second start on it raises Invalid_argument until the stop of the first app.

Async tasks

An 'a Async.t is a cold task: nothing runs until the runtime starts it with a cancel token. Thus update can make a task as a pure value, and the native tests can run it on a virtual clock. The token passes through let* with no extra argument. The design is close to the Task of Elm plus Process.kill. Brr's Fut does not fit, because a future starts at once and exists only in JavaScript.

module Async : sig
  type 'a t
  val return : 'a -> 'a t
  val fail : exn -> 'a t
  val map : ('a -> 'b) -> 'a t -> 'b t
  val bind : 'a t -> ('a -> 'b t) -> 'b t
  module Syntax : sig
    val ( let* ) : 'a t -> ('a -> 'b t) -> 'b t
    val ( let+ ) : 'a t -> ('a -> 'b) -> 'b t
    val ( and+ ) : 'a t -> 'b t -> ('a * 'b) t   (* the two run at the same time *)
  end
  val sleep : Span.t -> unit t
  val first : 'a t list -> 'a t                 (* the first ok; cancels the others *)
  val timeout : Span.t -> 'a t -> ('a, [`Timeout]) result t
  val make : (Cancel.t -> ok:('a -> unit) -> error:(exn -> unit) -> unit) -> 'a t
end

module Cancel : sig
  type t
  val cancelled : t -> bool
  val on_end : t -> (unit -> unit) -> unit   (* runs one time: at the cancel, or when the step ends;
                                               at once if t is cancelled *)
end

Rules

  • Token tree. The root token, an instance token, a task token, and a child token for each step of Async.make and for each branch of and+ and first.
  • End actions and long work. An end action runs at a cancel and also when the step ends normally. Thus a binding must not stop, in an end action, work that continues after its ok. For example, a fetch binding reads the body in the same step as the response, and its end action aborts the request only if the token is cancelled. Phase 0 found this rule: an abort at the end of a step that gave only the response headers would stop the download of the body.
  • Release. When a step, a branch or a task ends, its token detaches from its parent in O(1), is marked as ended, and runs its end actions. The children of a token are a doubly linked list. Thus a long-lived token does not collect old tokens, and a binding that removes a listener in on_end removes it also after ok. on_end on an ended or cancelled token runs the action at once.
  • Cancel of an ended token. A cancel of a token that a release already ended sets its cancelled flag, and it runs no action again. Cmd.latest needs this rule: the result of an ended task can still wait in the queue, and the drop check reads the cancelled flag. A unit test does a release, then a cancel, and expects cancelled = true.
  • Cancel order. A cancel first cancels the children, from the newest, and then runs the end actions of the token in the reverse order of registration. Each action runs once. An action that raises does not stop the others. The cancel uses an explicit stack, not recursion, thus a deep tree of tokens does not overflow the stack.
  • Once. The ok and error functions that make gives to the callback work one time only, and not after a cancel. A second call does nothing. If the token is already cancelled, make does not call the callback. If the callback raises after ok or error, the runtime writes the exception to the console. The callback keeps the continuations only in a cell that the end of the step clears. Thus a JS callback that never runs does not keep the continuation alive after a cancel.
  • No continuation inside the callback. ok and error put the continuation on the run queue. Thus the try of make covers only the user callback, and an error of a later step goes to the correct place.
  • Check at the run. A queued continuation examines the token of the task again when it runs. Thus a result or an error that was in the queue before a cancel does nothing.
  • Trampoline. bind starts its task and runs the next step at once only while the depth of synchronous steps is below a limit (for example 256). Above the limit, it puts the work on the run queue. Thus a long chain of let* does not overflow the stack under js_of_ocaml, for a right-nested chain (a loop) and for a left-nested chain (for example from List.fold_left).
  • Drain. The run queue drains in the settle step of each turn (section 11). A push outside a turn asks the host for a turn in a microtask. Thus a binding can call ok from any callback.
  • Combinators. Each branch of and+ and first has a child token and starts through the run queue. and+ cancels the other branch at the first error. first gives the first ok and cancels the other branches. If all branches fail, it gives the last error. first [] fails with Invalid_argument when the task starts.
  • Errors. An exception in a step goes to the error scope of the instance (section 09).

  queue_microtask : (unit -> unit) -> unit;            (* a turn for a push outside a turn *)
  post_task : (unit -> unit) -> unit;                  (* MessageChannel: the limit, a hidden tab *)
}
type ctx = { cancel : Cancel.t; host : host; run : Run_queue.t }
type 'a t = ctx -> ok:('a -> unit) -> error:(exn -> unit) -> unit

let bind (t : 'a t) (f : 'a -> 'b t) : 'b t = fun ctx ~ok ~error ->
  Run_queue.step ctx.run (fun () ->       (* the start of t: a left-nested chain stays flat *)
  t ctx ~error ~ok:(fun x ->
    Run_queue.step ctx.run (fun () ->     (* at once, or on the queue above the depth limit *)
      if not (Cancel.cancelled ctx.cancel) then
        match f x with
        | t' -> t' ctx ~ok ~error
        | exception e -> error e)))

let make (start : Cancel.t -> ok:('a -> unit) -> error:(exn -> unit) -> unit) : 'a t =
  fun ctx ~ok ~error ->
    if not (Cancel.cancelled ctx.cancel) then begin
      let step = Cancel.child ctx.cancel in        (* the resources of this step *)
      let cell = ref (Some (ok, error)) in       (* the only link from the callback *)
      Cancel.on_end step (fun () -> cell := None);
      let finish pick v =
        match !cell with
        | Some ks when not (Cancel.cancelled step) ->
            cell := None;
            Cancel.release step;                    (* detach in O(1), run the end actions *)
            let k = pick ks in
            Run_queue.push ctx.run (fun () ->      (* never inside the callback *)
              if not (Cancel.cancelled ctx.cancel) then k v)   (* check again at the run *)
        | _ -> () in
      try start step ~ok:(finish fst) ~error:(finish snd)
      with e -> if Option.is_none !cell then log_error e else finish snd e
    end

  • A second ok runs the continuation one time only. The error of a later step goes to the error function of that step.
  • An error that is in the queue before a cancel does not arrive
  • A result of Async.make in a click, in a timer callback and in a raw callback, and a raw Sub.run send: each message is processed in the same turn, with one render
  • A loop of messages stops at the limit after one render and continues in a new task
  • An on_end action after ok runs at once: 0 live listeners

  • The release of 10,000 sibling tokens, oldest first: 0.14 ms native
  • A fold of 100,000 nested and+: the start and the cancel do not overflow the stack.
A test with weak pointers (js_of_ocaml uses WeakRef, run with node --expose-gc) examined a cancelled task whose JS callback never runs. In native code, the continuation is freed. Under js_of_ocaml, it is freed when the callback is made in a library function, and also when the callback holds only a JS cell. A control case that is not cancelled stays alive, as it must.

Cancel.child, Cancel.release and Cancel.cancel are internal. Run_queue does not use Fun.protect, because Fun links Printf. Kilim_browser.Async.of_fut changes a Brr Fut.t into an Async.t. A JS promise cannot be cancelled: a task that waits on it stops at the cancel, but a promise that never settles keeps its JS callback until the page closes. Thus of_fut makes this callback with a JS expression that holds only a JS cell, and the cancel clears the cell. The promise then keeps only a small JS object.

Limit under js_of_ocaml: V8 keeps one shared context for the closures of one JS function. Thus a user callback of Async.make written inside update can keep the variables of update alive, also after a cancel (a test of the fifth review). Write each binding as a top-level function, as of_fut is. The leak tests run under js_of_ocaml with node --expose-gc.
Trade-off: async code is in monadic style with let*, not in direct style. Complex flows (retry, race, timeout) use the combinators first, timeout and and+.

Browser bindings: Brr

kilim uses Brr 0.0.8 or later for the DOM and the Web APIs. Brr supports wasm_of_ocaml since version 0.0.7.

Does Brr decrease the effort?

Yes. The port of webapi-gen was the largest single task of draft 1. With Brr, Phase 1 becomes an audit and a small set of hand bindings. Brr has documentation, an FFI manual and an FFI cookbook. The costs are small: Brr uses Jstr.t for strings and Fut.t for promises. The diff works on OCaml strings and converts only when it writes to the DOM.

The hot path under wasm_of_ocaml

Under wasm_of_ocaml, each DOM operation is a call from Wasm to JavaScript, and each string is copied and decoded from UTF-8. Under js_of_ocaml, an ASCII string goes across with no copy. kilim has these rules for the hot path:

  • The diff calls Jv.call, Jv.get and Jv.set with a literal method name and a literal array. js_of_ocaml changes such a call into a direct JS call with a constant name and no array. A test of the third review shows d.setAttribute("data-x", ...) in the output. Brr uses the same form on its own hot path.
  • The wasm_of_ocaml backend makes a fixed-arity JS fragment from the same form. The reviewer read this in the source of js_of_ocaml 6.4.1, not in a build. Phase 0 makes a check of the generated code.
  • kilim has no JS file with external functions. wasm_of_ocaml would need a second version of each such function in a .wat file.
  • The JS values that kilim.browser needs (document, Object, the SVG namespace, the shared functions of the queues) are made one time, and lazily: the module initialization reads no document, thus node can load the library. The event walk is OCaml code of the core.
  • No == on a JS value: under wasm_of_ocaml it is not the JS identity. Jv.strict_equal is the only identity of two nodes.
  • The page controls the values that kilim.browser reads, and under wasm_of_ocaml a cast of a JS value of the wrong type (for example Jv.to_string of a number) is a trap, not an OCaml exception. Thus each read examines the JS type first and has a safe default: the value of a progress or of an li is a number, thus the diff compares String(value), and a string payload is "" for a value that is not a string. kilim.browser compares the type, the name and readyState as JS strings, with no conversion. A control of a form with the name of a property hides that property of the form ([LegacyOverrideBuiltIns]): a form whose __kilim is an element has no cell, and a control named parentNode is not supported.
  • A trap that still occurs goes past each OCaml catch and leaves its turn open: then the app would stop. A JS guard around each entry point needs JS code, thus eval (which a strict CSP refuses) or a JS file of externals (which wasm_of_ocaml would need again in a .wat file). The browser already reports the exception of each listener and each callback of the host with an error event on window (an unhandledrejection event for a trap in a promise reaction, for example a start in the promise of the loader). The event can come inside a live turn: a listener of the page that an update reaches through a synthetic event traps, the dispatch reports it, and the update goes on. A stack of markers at the entry points cannot tell the two cases apart, because such a listener is not an entry point of kilim. Thus, for a WebAssembly.RuntimeError, kilim.browser queues Runtime.abort in a microtask. A microtask runs only when the JS stack is empty: then each turn that is still open is dead, and a live outer turn already ended. Runtime.abort ends each open turn as the catch of a turn does, resets its run queue, gives the error to the error handler, and asks for a turn if work stays in a queue (also when a microtask turn of kilim ran between the trap and the abort and only queued its work). The listeners exist one time for the page, only in the wasm_of_ocaml build, and only if WebAssembly exists: the js_of_ocaml build has no traps, and a page with no WebAssembly (Chrome with no JIT, Firefox with WebAssembly off) runs only that build. Another error does not abort, with one exception. WebKit (Playwright WebKit 27.2) gives a trap of a wasm:js-string function (the cast of a value that is not a string) as an error event whose error is null, with the message "Script error.", as for an error of a script of another origin. Thus, for an error event with a null error, kilim.browser queues Runtime.abort_open in a microtask: it calls Runtime.abort only if a turn is still open, with an error that has the message of the event. This is correct for each such event, whatever its cause: in the microtask, each open turn is dead. With no open turn, the event is not a trap of a turn, and it gives no report. Two such traps in one task give one report, because the two events do not tell which error they carry. A start records the app (its mark on the element and its listeners) before the first turn, thus a trap in init or in the first view leaves an app that stop can end.
  • The diff works on OCaml strings and converts a string only when it writes it.
  • Brr stays for the other APIs: fetch, history, storage, sockets and timers.
  • The core gives each delay as an int number of milliseconds, thus the browser host does not round.

DOM safety

The escape rules of caravan.html are for HTML text. A DOM renderer has different risks. kilim has these rules:

  • An allowlist of HTML and SVG element names. A name that is not on the list raises. The list does not contain script, iframe, object, embed, base, meta and link. It also does not contain the SVG animation elements (set, animate, animateMotion, animateTransform), because they can change a checked href after the check. kilim has no El.script.
  • All name checks ignore case, because HTML changes attribute names to lowercase. El.v gives the usual spelling of an element name, for example foreignObject for "FOREIGNOBJECT". Thus the namespace and the compare of the diff do not change with the case.
  • At.v refuses on* names and srcdoc. It also refuses a name that is not a valid XML name (for example "data-a b"), because setAttribute throws for such a name.
  • A URL check for each URL attribute: href, src, action, formaction, poster, cite, data, background, ping, and each URL of srcset. The permitted schemes are http, https, mailto and tel, and relative URLs. At.v refuses a name with :, thus SVG uses href, not xlink:href.
  • The URL check finds the scheme as the WHATWG URL parser does. First it removes the C0 control characters and spaces at the start and at the end, and all tab and newline characters. Then it reads a scheme: an ASCII letter, then letters, digits, +, - or ., then :. It compares the scheme with no case. If it finds no scheme, the URL is relative. Thus " javascript:" and "java\tscript:" are refused.
  • Text nodes need no escape. The text of a style element is CSS: do not put data of a user in it.
  • The API has no innerHTML and no generic property setter, except an explicit View.unsafe_html. It takes a value of the type Unsafe_html.t. In the core, this type is a record of the HTML string and an optional native value. Unsafe_html.of_string (core) makes one for a page with no Trusted Types. Kilim_browser.Unsafe_html.of_trusted takes a TrustedHTML from the policy of the app (with its own sanitizer), and it stores the value and its string String(v). If trustedTypes exists, a value that is not a TrustedHTML raises Invalid_argument. If the page has no trustedTypes, the value keeps only the string: thus a small polyfill that gives strings works. A CSP with require-trusted-types-for 'script' refuses a plain string in innerHTML. kilim makes no HTML policy of its own. The diff compares the strings: if they are equal, it writes nothing. Thus a new TrustedHTML on each render does not reset the selection, the focus or the scroll inside the HTML. If the string changed, the diff writes the native value when it exists. The string renderer and the test host use the string. The Trusted Types CI test includes a View.unsafe_html node.
  • A refused name or URL raises Invalid_argument in view. The error scopes (section 09) then apply.
Later: webapi and webapi-gen come after version 1. Generated bindings can then extend or replace kilim.web.

Answered questions

You answered the four open questions of draft 7. The decisions section shows the answers too.

  1. License. MPL-2.0 only, as caravan.
  2. Render timing. Agreed: a synchronous render for discrete events and one render for each frame for other events. In a hidden tab, the render runs in a new task (section 11).
  3. Tasks and the model. A task only sends messages. It cannot read the model of its instance. Thus update stays the only place that reads and changes the model.
  4. Interop. Async.t converts only from Brr Fut.t, with Kilim_browser.Async.of_fut. No conversion for Lwt or other promise libraries in version 1.

The plan has no open question at this time.
